# API доработки в amoCRM

Genezis, 21:33. [Транскрипт](transcript.md), [страница](page.md).

## API и webhook

Через API программа запрашивает данные CRM или меняет их командами. Например, заявка сайта создает сделку, контакт, задачу и примечание, передает маркетинговые метки (00:31–02:14).

Webhook отправляет уведомление внешнему адресу после события. При смене этапа CRM может вызвать скрипт, который обновит статус заказа на сайте (02:14–04:03).

Можно отслеживать события всего аккаунта либо отправить webhook из DP на нужном этапе с условиями. Точечный запуск сокращает лишнюю обработку. Эти способы работают вместе: уведомление запускает обработчик, API позволяет прочитать или изменить данные.

## Нужна ли своя разработка

Сначала проверить стандартные настройки и маркетплейс. Индивидуальная интеграция может понадобиться для самописной ERP, бухгалтерской системы или особой отчетности, для которых нет готового решения. Иногда достаточно попросить автора существующего виджета добавить нужную функцию (04:35, 11:25–12:32).

Проект может не окупиться, если функции не используют, неверно оценен объем, не обеспечена поддержка или задачу уже решает готовый виджет. История с исчезнувшим подрядчиком показывает риск поддержки; она не доказывает, что отдельные специалисты всегда неподходящие (10:10–12:02).

## Стоимость и польза

В бюджет входят анализ, разработка и тестирование. Стоимость зависит от сложности, времени, опыта команды и технологий. Платные внешние API добавляют расходы, а обслуживание и обновления после запуска нужно считать отдельно. Связанные сервисы меняют API, интеграция может потребовать правок (05:06–07:19).

Ожидаемая польза может состоять в сокращении ручного ввода, более быстром обслуживании, меньшем числе ошибок и возможности подключать новые источники без переделки системы (07:19–10:10).

Сэкономленные часы можно перевести в денежную оценку. Но польза зависит от того, как компания использует освободившееся время. Рост продаж из-за ускорения обработки в уроке предполагается автором; его нужно измерять у клиента. Для окупаемости сравнивают затраты на разработку и поддержку с ожидаемыми выгодами.

## ТЗ и работа с разработчиками

Сначала сформулировать бизнес-цель и функции, затем написать ТЗ, согласовать сроки, этапы и цену, оценить окупаемость. Разрабатывать и принимать по этапам, оплату можно связать с их результатами (12:32–15:17).

ТЗ должно описывать точки интеграции, какие данные передаются и возвращаются, примеры запросов и ответов при необходимости, авторизацию и безопасность. В уроке упомянуты OAuth 2 и токены. Также нужны обычные сценарии, ошибки и сетевые сбои. Фраза «Сделать красиво и чтобы все летало» не описывает, какой результат нужно получить и проверить.

Для работы нужен общий список задач со статусами, регулярные встречи и короткие отчеты «Сделано / План / Проблемы». После каждого этапа смотреть демонстрацию и проверять результат. Условия поддержки и будущих изменений согласовать заранее (15:17–17:29).

## Примеры заказных решений

У производителя химического сырья связали товары с поставщиками, упростили подбор и сохранение данных доставки. Автор сообщает уменьшение ошибок и высвобождение времени закупщиков (18:02–18:34).

В магазине одежды синхронизировали свою систему заказов со сделками, этапами, воронками и ответственными разных отделов, добавили подбор по актуальным остаткам. Это сокращает ручное сопоставление двух систем (18:34–19:39).

Для сети автостекольных станций филиалы хранят в списках. По адресу заявки выбирают филиал, передают ее в его аккаунт, возвращают в головной статусы, примечания и звонки. Здесь разработана синхронизация нескольких аккаунтов; одной ролью пользователя это не настраивается (19:39–20:46).

До заказа нужно ответить: какой ручной шаг или ошибка исчезнет, какие данные и событие нужны, почему готовое решение не подходит, как принять результат и кто будет поддерживать его после запуска. Без этих сведений постановку еще нужно уточнять.

## Что добавляет документация платформы

[Обзор возможностей](../../../docs/amocrm/developers/content/crm_platform/platform-abilities.md) прочитан 2026-10-08. Интеграция хранит данные приложения и ключи OAuth; JS-виджет необязателен. Приватная интеграция предназначена для одного аккаунта и не публикуется в маркетплейсе. Публичная проходит модерацию. Внешняя работает через API без JS-виджета, создается через кнопку авторизации. Отраслевое решение настраивает новый аккаунт, требует согласования и модерации.

Поэтому в ТЗ нужно уточнить, нужен ли только обмен данными или еще интерфейс в CRM, и для одного или нескольких аккаунтов делается решение. Наличие API не требует обязательной разработки виджета.
