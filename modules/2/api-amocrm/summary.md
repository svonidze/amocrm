# API доработки: необходимость, стоимость и организация

Урок Genezis, 21:33. Источники: [транскрипт](transcript.md), [страница](page.md). Индивидуальная интеграция нужна, если стандартные возможности и готовые решения не закрывают конкретную потребность бизнеса. Ее оценивают вместе с поддержкой и пользой для процесса.

## API и webhook

**API** позволяет программе запросить данные CRM или изменить их командами. Пример: заявка с сайта создает сделку, контакт, задачу и примечание, передает маркетинговые метки (00:31–02:14).

**Webhook** уведомляет внешний адрес о событии. Пример: статус сделки изменился, CRM отправляет уведомление скрипту, тот меняет статус заказа на сайте (02:14–04:03).

Отслеживание можно настроить на уровне аккаунта либо точечно через Digital Pipeline. Если реакция нужна только на определенный этап и условия, точечный запуск сокращает лишнюю обработку. API и webhook часто работают вместе: событие запускает обработчик, а команды читают и обновляют нужные данные.

## Когда выбирать доработку

Сначала проверить штатные настройки и маркетплейс. API подходит, например, для самописной ERP, уникальной бухгалтерской системы или отчетности без готовой интеграции. Иногда быстрее попросить автора публичного виджета расширить готовое решение (04:35, 11:25–12:32).

Причины неокупаемости (10:10–12:02): функции без сценария использования, неточное планирование, неподходящий подрядчик и отсутствие поддержки, разработка того, что уже решается готовым виджетом. Пример автора с исчезнувшим подрядчиком иллюстрирует риск передачи поддержки, а не доказывает непригодность всех отдельных специалистов.

## Из чего состоит стоимость и эффект

Стоимость зависит от сложности, времени анализа/разработки/тестирования, опыта команды, технологий и платных внешних API. Отдельно учитываются обслуживание, обновления и изменения API связанных сервисов (05:06–07:19).

Для оценки эффекта автор предлагает считать (07:19–10:10):

- Сокращение ручного ввода и переноса данных. Часы сотрудников переводятся в денежную оценку.
- Скорость обслуживания и возможное улучшение клиентского опыта.
- Снижение ошибок и стоимости их исправления.
- Возможность масштабировать процессы и подключать новые источники.

Заявление о влиянии ускорения на продажи передает предположение автора: фактический эффект нужно измерять у клиента. Время окупаемости оценивают сравнением затрат на разработку и поддержку с ожидаемыми выгодами. Экономия времени имеет ценность при реальном использовании высвободившегося ресурса.

## Постановка и этапы проекта

Последовательность (12:32–15:17):

1. Сформулировать бизнес-цель и нужные функции.
2. Составить подробное ТЗ.
3. Согласовать сроки, этапы и стоимость.
4. Оценить окупаемость, включая поддержку.
5. Делать по этапам, проверять результат каждого и договориться о соответствующей оплате.

ТЗ должно описывать точки интеграции, передаваемые и возвращаемые данные, при необходимости примеры запросов/ответов, авторизацию и безопасность (в уроке упомянуты OAuth 2 и токены), нормальные сценарии и обработку ошибок/сетевых сбоев. Фраза «Сделать красиво и чтобы все летало» не позволяет проверить результат.

Для взаимодействия с разработчиками выбрать общий список задач и их статусов, регулярные встречи и краткие отчеты «Сделано / План / Проблемы». Проводить демонстрации и тестирование промежуточных результатов, заранее определить условия дальнейшей поддержки (15:17–17:29).

## Три примера реализации

**Закупка химического сырья** (18:02–18:34): связать товары и поставщиков, облегчить выбор поставщика и сохранить сведения доставки. Автор сообщает снижение ошибок и освобождение времени закупщиков.

**Интернет-магазин одежды** (18:34–19:39): синхронизировать самописную систему заказов со сделками, этапами, воронками и ответственными разных отделов; учитывать актуальные остатки при подборе. Сокращается ручное сопоставление двух систем.

**Сеть автостекольных станций** (19:39–20:46): справочник филиалов хранится в списках, заявка распределяется по адресу в аккаунт филиала, головной аккаунт получает статусы, примечания и звонки для контроля качества. Это индивидуальное решение синхронизации нескольких аккаунтов, а не простая роль пользователя одного аккаунта.

## Практический вопрос перед заказом

Какой конкретный ручной шаг или ошибка исчезнет, какие данные и событие нужны, почему готового решения недостаточно, как проверить результат и кто поддерживает его после запуска? Если ответы отсутствуют, нужно доработать постановку задачи до оценки разработки.
